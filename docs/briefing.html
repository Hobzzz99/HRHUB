Project Briefing

TalentFinder

Automated candidate sourcing, scoring and ranking

A recruiter types the requirements for a role. The system finds candidate profiles, extracts each into structured data, scores every candidate on four weighted dimensions, discards the ones failing a hard requirement, and returns a ranked shortlist with a written justification for each person.

This document is for understanding the whole system well enough to explain and defend it: what it does, how it is built, what it costs, where it is fragile, and which decisions are still open.

1. Executive summary

The pitch

Recruiters spend most of their sourcing time reading profiles that were never going to fit. This automates that first pass and returns a ranked shortlist where every candidate carries a match percentage, a breakdown of why, and the specific things they have and lack.

The three things that matter most

1. The valuable part is the scoring engine, not the scraper. The data source is a swappable component. Matching, ranking and explanation work identically whether profiles come from LinkedIn, a paid vendor, or your own applicant database. Adding a source is one class with two methods. The asset survives any decision about where data comes from.

2. Every score is explainable and reproducible. No black box. A candidate scoring 92 has a stored breakdown showing exactly which component contributed what, and the rules are versioned, so a score from six months ago still means something. This matters commercially and legally — automated decisions about people need to be defensible.

3. The LinkedIn path is the riskiest component. It breaches LinkedIn's terms and gets accounts restricted — twice so far. The code takes that seriously: a hard hourly cap, manual sign-in, no stored passwords, and an account-rotation path. But no amount of engineering makes it safe, and section 14 is the honest recommendation.

2. What a recruiter actually does

  1. Describe the role. Job title, optional keywords, qualifications, minimum experience, location, employers, graduation-year window.
  2. The search runs in the background. A browser opens on their own machine; the first run of the day asks them to sign in to LinkedIn by hand. Progress streams live.
  3. Read the ranked results. Each candidate shows a match score, the four-part breakdown, matched and missing keywords, and plain-English reasons.
  4. Save and export. Shortlist to a saved list, or straight to CSV.
The one field people get wrong

Critical skills are pass/fail, and separate entries mean all of them. Three entries — CPA, ACCA, ESAA — requires a candidate to hold all three, which is nobody. To accept any of several qualifications, put them in one entry: CPA / ACCA / ESAA. The form now shows the logic as it is typed and warns when an unintended "and" has been built.

  Server (shared)                      Recruiters' laptops
  ┌────────────────────────┐          ┌──────────────────────────┐

  │ Next.js  web app       │          │   own LinkedIn account   │
  │ FastAPI  API           │ ◄─ SSH ─►│   own hourly budget      │
  │ Postgres shared data   │  tunnel  │   drives the browser     │
  │ Redis    job queue     │          └──────────────────────────┘
  └────────────────────────┘

Why the split. Sign-in and CAPTCHAs are cleared by a person in a visible browser window. A server has no screen, so the scraper cannot live there. Everything shared — the database, the web app, the queue — does.

Why per-recruiter queues. A search runs only on its owner's laptop. Celery's default hands any job to any free worker, which here would load one recruiter's LinkedIn session into a colleague's browser on a different IP — unusable, and close to the textbook signal of a stolen account.

4. The search pipeline

Six stages. If you can narrate these, you can answer almost any question about behaviour.

StageWhat happens
1. SearchOnly the job title goes in the search box. Employer and location are applied through LinkedIn's own filters, which restrict server-side so unqualified people are never opened.
2. Pre-filterDeliberately timid — discards a card only when it clearly contradicts a stated requirement. A false negative here is invisible and unrecoverable; a false positive costs one page load.
3. FetchChecks the cache first. A profile collected in the last week is reused and costs nothing — no page load, no budget, no exposure.
4. ScoreFour weighted components. See section 5.
5. FilterHard requirements: qualifications, employer, experience, career stage, score threshold.
6. StoreRanked and written with the score breakdown, the reasons, and the version of the rules used.
Two behaviours worth knowing by heart

Partial results beat failed searches. If the hourly budget runs out mid-search, or the account is restricted, or the machine dies — everything collected so far is kept and stored. Because profiles are cached, re-running picks up where it left off rather than paying again.

One bad profile does not kill a search, but several in a row stop it. A single unreadable profile is skipped; three consecutive failures mean something systemic — an expired session, a layout change — and continuing would spend the rest of an hourly budget repeating one failure.

5. The matching engine

Everything else is plumbing. This is the part that produces the number a recruiter acts on.

ComponentWeightHow it is computed
Title30%Split into what the job is and how senior it is, scored separately. The domain is a gate: no evidence of the work scores zero, however senior. Judged across the whole career.
Keywords30%Fraction found in the candidate's name, headline, job titles, skills and certifications. Tolerates word forms — "vendor management" matches Vendor Manager.
Experience30%Total years against the minimum, capped. Overlapping roles merged and career gaps excluded, so nobody is credited twice for two jobs at once.
Location10%A preference, not a filter, unless the strict switch is on.

Any component left blank is dropped and its weight redistributed. Nobody is marked down for failing a requirement that was never set — which is what makes the optional fields genuinely optional.

What v4 fixed, and why it took real data to find

Three defects, all found by measuring rather than reading the code

1. "Manager" is not a job. A search for external audit manager returned Finance Managers, because both share a word that describes a level and appears in every hierarchy. Domain and seniority are now separate, and the domain is a gate.

2. A self-declared skill tag is not a career. Six candidates cleared the gate on a LinkedIn tag reading "External Audit" with no supporting job history. Skills now count for keyword matching, not for the profession gate.

3. At an audit firm, external audit is called "Audit". The most serious. Demanding the literal word discarded 28 audit managers at the exact four firms the recruiter asked for. An unqualified audit role now reads as external audit unless the career says "internal" — which internal auditors always do, because theirs is the variant needing a label.

Know this for the room

CPA is the American qualification. Across the 237 profiles: CPA 42, ACCA 21, DipIFR 16, CIA 8, ESAA 5. For Egypt and Saudi Arabia, CPA / ACCA / ESAA is the honest default and CPA alone is a US filter.

6. Telling the truth about failure

This is the part that separates a tool recruiters keep using from one they abandon, and it was the largest single piece of recent work.

A search used to have two outcomes: it finished, or it crashed. Anything in between — a filter that never reached LinkedIn, a session that expired half-way, a results page that did not render — finished, and produced the same message: 

"No candidates matched. Try lowering the minimum score or experience."

That sentence blames the recruiter's criteria for a technical failure. A recruiter told it twice concludes the market is empty, or the tool does not work, and they are right to.

What happenedWhat the recruiter is told now
Nobody matchedWhich filters rejected people and how many — "8x works at a different employer, 2x missing a required qualification"
A filter could not be applied"These results are not what you asked for", above the results, plus how to work around it
Hourly limit reachedThat it was cut short, that the criteria are not the problem, and when it resumes
Account restrictedThat it stopped and that collected work was kept
Their machine diedThat it stopped unexpectedly and re-running will not repeat the cost
The principle

"No mistakes" is not achievable — the data source is someone else's website and it will change without notice. What is achievable, and what is now built: the app never presents an unreliable answer as a reliable one.

And when the machine simply vanishes

A worker that dies mid-search used to leave the search saying "running" for ever. A sweep now marks abandoned runs failed, measured from the last progress update, so a slow search is never reaped out from under itself. Job redelivery is disabled deliberately: re-running a search re-opens profiles, re-spending budget that takes an hour to refill, and would collide with the results the first attempt already stored.

How the scraping is kept survivable

LayerWhat it does
The volume capThe control that actually matters. A hard hourly ceiling, counted in a rolling window persisted to disk so it survives restarts. Volume is what abuse detection keys on.
Manual sign-inThe app never types a password. A person signs in and clears the CAPTCHA. There are no stored credentials to leak.
Human behaviourCurved pointer paths, inertial scrolling, irregular pacing with pauses, honeypot checks before clicking.
Fingerprint consistencyOne stable machine identity per account, distinct between accounts — so a restriction on one does not link to the next.
The ceiling, stated plainly

Throughput scales with recruiters, not with hardware: each account has its own hourly allowance. Five recruiters is five times the rate — and five personal accounts at risk. That is the trade this design makes, and it is the reason section 14 exists.

8. Quality: what 419 tests cover

AreaWhat is pinned
Scoring and filteringEvery component, the weights, the domain gate, credential alternatives, the employer guarantee.
Experience mathsOverlapping roles, career gaps, a dozen date formats.
The truth-tellingThat a degraded run cannot report itself as an ordinary empty one; that repeated failures stop a run.
Failure recoveryAbandoned searches reach a terminal state; a slow one is not reaped.
Data protectionDeletion removes every copy; retention never deletes work in use; one recruiter cannot read another's sourcing.
ReadinessThat it fails when a dependency is down — a health check that cannot fail is worse than none.

What is not tested, stated honestly

The scraper's selectors. They depend on LinkedIn's live markup, which no test can pin — a test would only assert that today's HTML looks like today's HTML. This is covered by debug dumps written on failure and by the degraded reporting, not by tests, and it is the part most likely to break.

9. Data protection and retention

The system stores real people's professional histories. Three obligations, all now implemented rather than promised:

ObligationHow it is met
Deletion on requestA candidate can be erased: their profile, every search result referencing them, and every recruiter's saved copy. Logged, because the record that would prove the request was honoured is the one being destroyed.
Retention limitProfiles nothing references are deleted after six months. Previously nothing ever removed a candidate — the cache window only re-scraped them.
Data minimisationThe raw collected payload is discarded once a profile is old enough to be re-fetched rather than reused.
Access controlA recruiter can read candidates from their own searches and saved lists. Profiles are shared internally for efficiency but not readable by id alone.

10. Deployment and operations

The server runs five containers behind TLS: web app, API, Postgres, Redis and a reverse proxy that obtains its own certificate. Database and queue are bound to loopback and reached from recruiters' laptops through an SSH tunnel — nothing but ports 80 and 443 is exposed.

Operational concernHow it is handled
Is it actually working?A readiness endpoint that checks the database and queue and returns an error when either is down. Liveness is separate and dependency-free, so a blip does not get a healthy process killed.
Setting up a laptopA preflight script checks Python, the browser, the tunnel, the state directory and the power settings, and prints the fix for each failure.
Diagnosing a bad searchThe worker writes a dated log file — the only place a stack trace is captured anywhere in the system.
When something breaksA runbook starting from the report you will actually get: "my search did nothing", which now has six distinguishable causes.
BackupsA nightly dump with retention, empty-dump detection, and optional off-site copy. It must be installed and rehearsed — an untested backup is an assumption.

12. Legal and compliance

Scraping LinkedIn breaches its User Agreement. Raise this yourself rather than let it be discovered. Three concrete consequences:

  1. Account restriction. Happened twice. Recoverable only by the account's owner, usually with identity documents.
  2. It becomes the company's breach. Rolling out company-wide moves this from one person's account to the company, at company direction, using employees' personal accounts.
  3. Personal data obligations. Collecting professional histories at scale carries them regardless of source. Section 9 covers what is built.

This document is engineering analysis, not legal advice. A lawful basis and jurisdiction-specific obligations should be confirmed with counsel before processing real candidate data at scale.

13. Known limitations

LimitationSeverityDetail
Scraping does not scaleHigh A fixed hourly ceiling per account, and each account is a person's own. Structural, not a tuning problem.
Extraction will breakHigh Depends on LinkedIn's markup. Twice already. Debug dumps make repair quick, but it is unplanned work on someone else's schedule.
The employer filter needs a manual stepMedium Restricting to named firms works reliably by pasting a LinkedIn URL — ten seconds. Driving the filter panel automatically is unproven, and the app says so when it fails.
No labelled accuracy benchmarkMedium About an hour of a recruiter's time would produce a defensible single figure. Until then, only the specific measured results can be claimed.
Binary location scoringMedium No concept of distance or commuting range — "Berlin" and "Munich" are equally wrong.
Not yet deployedMedium Runs on a developer machine. Deployment is documented and needs a server and about an hour.
Accounts burn faster than they rotateHigh Rotation defeats device correlation only. The IP is unchanged, so each replacement is more exposed than the last. A supply problem, not a bug.

14. Where I would take it next

Immediate — days, independent of any strategic decision

  • Deploy to a small server and run it for two weeks with one or two recruiters.
  • Label 50 candidates to get a defensible accuracy figure.
  • Install and rehearse the backup restore.

Short term — weeks

  • Finish the automatic employer filter, or accept the paste-a-URL step as the supported path.
  • Roll out laptop by laptop, each with the preflight check.

Strategic — the decision that unblocks everything

Choose where candidate data comes from

Everything difficult about this system traces to one choice: we collect the data ourselves from a site that does not want us to. That is what caps throughput, what puts recruiters' personal accounts at risk, what makes it a terms breach, and what breaks without warning.

Buying from a licensed provider removes all four at once, and nothing else about the product changes — the source was built as a replaceable component from the start, precisely so this decision could be made late and commercially rather than early and technically.

The ask: approval to evaluate providers and a budget range, plus a decision on whether recruiters' personal LinkedIn accounts may be used meanwhile.
